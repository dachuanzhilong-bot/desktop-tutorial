# QUALITY — 解の本当の誤差を測る物差し

REFACTOR_PLAN ステップ 3-0 の成果物。出荷しているポストフロップ解（`web/public/postflop`）の誤差を、**サンプルしたカードの中だけでなく、全ターン・全リバーカードで**測る。フェーズ 3 のほかのステップ（EQR の見直し、全カードで解く、ベットサイズ）は、この表の数字で前後を比べる。

> **現状: 3 シナリオ・63 / 63 フロップを計測済み**（§5）。未計測のフロップは無い（§7）。

## 1. 物差しの定義

- **exploitability（チップ）** = 「OOP の最適応答の値 − OOP の今の値」＋「IP の最適応答の値 − IP の今の値」。片方の戦略を固定して、もう片方が最善の手で応じたときに増える値を、**2 人分足したもの**（平均ではなく和）。`Solver::exploitability`（`solver/src/postflop.rs`）と同じ定義。均衡なら 0。
- **ポット比 %** = `100 × exploitability ÷ フロップ開始時のポット`（`srp` は 5.5bb、`3bp` は 22.5bb）。`index.json` の `stats[*].exploit` と `docs/08` §5 の値と同じ単位。
- 値は「最終ポットの取り分 − ポストフロップで入れた額」（`docs/08` §1）。2 人の今の値の和は常にポット額（定和）。測定のたびにこれを確かめている（出力の `base`）。
- **サンプル内の値**: 出荷時と同じ木（ターン 6 枚・リバー 2 枚のサンプル、サンプルの重み `(残り枚数 / サンプル数) / (残り枚数 − 4)`、フロップのオールインは固定サンプル 120 通り）の中で測った値。`Solver::exploitability` そのもの。
- **全カードの値**: 同じ戦略を、実際の配り方（ターン 49 枚 × リバー 48 枚 = 2,352 通り、重み `1 / (残り枚数 − 4)`。フロップのオールインは全 1,176 ランアウト、ターンのオールインは全リバー）で測った値。サンプルに無いカードでの戦略は §3 の規則で割り当てる。**これが「本当の誤差」の物差し。** 目標は全フロップで 0.3% 以下（REFACTOR_PLAN「目標の決め方」）。
- どちらも**決めたベットサイズの中での**最適応答（`docs/08` §2 の抽象化）。別のサイズで打つ相手に対する誤差は含まない。

## 2. 測る戦略はどこから来るか（計画との違い）

計画では「出荷ファイル（`TSP1`）の戦略を読んで固定する」としていた。実際に読むと、**出荷ファイルは決定ノードの約 4% しか持たない**（全 63 フロップの合計で 4.6%。§5 の要約。例: `srp-btn-bb` の As7d2c は木の 3,486 決定ノードのうち 135）。`export` が到達確率 0.4% 未満のラインを書き出さないため（`docs/08` §4、`TSP1` の子コード `-2`）。最適応答は、相手の戦略が固定されたまま自分だけがそのラインに入れるので、書き出されなかったラインの戦略も必要になる。そこをチェック・コールなどの既定の戦略で補うと、**サンプル内でも 68〜560%**（63 フロップ） になり、物差しにならない（出力の `fileOnlyInSamplePct`）。

そこで `measure_exploit --pre <プリフロップ解>` は、そのフロップを `gen_postflop` と**同じ手順**（同じレンジ、同じ木と乱数の種 `11 + フロップ番号`、1,400 反復、700 反復目で平均を取り直す）で解き直し、**書き出したバイト列が出荷ファイルと 1 バイトも違わない**ことを確かめてから、その戦略（書き出されなかったラインを含む、ソルバーが持っていた戦略全体）で測る。一致しなければそのフロップはエラーで止まる。計算は決定的（同じ入力・同じ順の浮動小数点演算）なので、一致は「出荷した戦略そのもの」の確認になる。計測した 63 フロップはすべて一致した。解データは読むだけで、何も書き換えない。

- **開始時のレンジ**: `--pre` では、解き直したソルバーの開始レンジ（`Solver::prior`）をそのまま使う。ファイルだけで測るとき（`fileOnlyInSamplePct` と `--pre` なし）は、OOP はルートの重み、IP は「IP の最初の判断」の重みを読む。IP はまだ動いておらず、フロップではカードも配られないので、この重みは OOP の最初のアクションによらず IP の開始レンジに等しい。そこで OOP のチェックの後のノードを読み、**それがファイルに無ければ、OOP の次のアクション（ベット）の後の IP のノードを読む**。
- この補いは、`3bp-btn-bb` の 5c3d2h（#18）と 5c5d2h（#19）のために足した。この 2 フロップでは OOP がほぼ必ずベットし、解き直しで求めたチェックのラインの到達確率が 0.00303 と 0.00002（書き出しの閾値 0.004 未満）なので、出荷ファイルにはチェックの後の IP のノードが無い（ルートのチェックの子コードが `-2`）。以前のツールはそのノードだけを読んでいたため、この 2 フロップは「IP's first decision missing」で止まっていた。チェックの後のノードがある 61 フロップでは読む場所が変わらないので値も変わらない（`3bp-btn-bb` #2・#20 を直した後のツールで測り直し、時間以外の全項目が以前の行と一致した）。テストは `ip_range_without_the_check_line_in_the_file`（§4）。

- プリフロップ解は `web/public/solutions/cash6max-100bb/` を `gzip -dc` で展開したもの（`manifest.json` と `chunk-N.bin`）。切り出したレンジの幅（BB 54.4% / BTN 47.3% など）は `index.json` の `oopPct`・`ipPct` と一致する。
- `--pre` を付けないと、ファイルだけで測る（上の既定で補う）。数字は参考にならないが、ファイルの読み込みと対応付けの検査になる。

## 3. サンプルに無いカードの戦略の割り当て

木はサンプルの木をそのまま使い、実際に配られたカード `c` ごとに、そのチャンスノードのサンプルの子のどれかに入る。

1. **サンプルのカードなら、そのもの**。
2. そうでなければ、サンプルのカード `s` のうち、次の順に比べて一番小さいものを選ぶ（`Assign::Nearest`、`solver/src/measure.rs` の `assign_card`）。
   1. **フラッシュの段階が違うか**: 段階 = 「そのカードを足したボードで、そのカードのスートの枚数 − 2」（0 未満は 0）。0 = ボードにフラッシュが無い、1 = 3 枚目（フラッシュが可能になる）、2 = 4 枚目、3 = 5 枚目。
   2. **ランクの差** `|rank(c) − rank(s)|`。
   3. **ペアの段階が違うか**: そのカードと同じランクがボードに何枚あるか（0 = ボードをペアにしない、1 = ペアにする、2 = トリップスにする）。
   4. **層が違うか**: 生成時の層（`pick_cards`: 残りのカードを (ランク, スート) の降順に並べて等分したもの）が同じサンプルを優先。
   5. サンプルの並び順（決定的にするため）。
   つまり「同じランクの別スートのサンプルがあればそれ。無ければランクの近いサンプル。ただしフラッシュの有無が変わるサンプルは避ける。同点ならボードのペアの有無が同じ方、生成時の層が同じ方」。
3. **手札の読み替え**: 実際のボードと、割り当てたサンプルのボードは、ターン（・リバー）のカードだけが違う。カードの置換 `board_perm`（実際のターン → サンプルのターン、実際のリバー → サンプルのリバー、ほかは恒等。サンプルのカードを持つ手は、実際のカードを持つ手に読み替える）で、実際の各コンボを「サンプルのボードでの同じ（または読み替えた）コンボ」に対応させ、その戦略を使う。生きているコンボどうしの 1 対 1 対応になる。
4. リバーの割り当ては、ターンを置換で移した後のサンプルの世界で行う（実際のリバーがサンプルのターンと同じカードのときは、実際のターンのカードとして扱う）。
5. 比較用に、生成時の層のサンプルだけを使う規則（`--assign stratum`）もある。表は `Nearest` の値。

### 割り当ての限界

- サンプルはターン 6 枚・リバー 2 枚しかない。割り当て先のボードでは、**同じ 2 枚の手札でも役が違う**ことが多い（例: 実際のリバーでストレートが完成したのに、割り当て先では完成していない）。固定した側はその手を「割り当て先での強さ」で打つので、最適応答はそこを突く。全カードの値には、**サンプルの近似そのものの誤差と、この割り当て規則の粗さの両方**が入る。もっと賢い割り当て（スートの同型を使う、役の強さで並べ直すなど）なら値は下がりうるので、この値は「今の出荷データ + この規則」の値であって、サンプル方式の下限ではない。
- 逆に、フラッシュの段階で揃えても、手札のどのコンボがフラッシュになるかはスートが違えば変わる（読み替えはカードの置換で、スートの置換ではない）。フラッシュドローの価値の違いを完全には拾っていない。
- 解き直しと全カードの値は、どちらも「決めたベットサイズの中」の値。ベットサイズの抽象化による誤差は測っていない（過小評価の方向）。
- 単精度の累積なので、2 人の今の値の和はポットと 1e-3 程度ずれる。表の 3 桁目までは影響しない。

## 4. 測り方（再現手順）

```bash
cd solver
cargo build --release --bin measure_exploit
mkdir -p out/pre/cash6max-100bb
for f in ../web/public/solutions/cash6max-100bb/*.gz; do gzip -dc "$f" > out/pre/cash6max-100bb/$(basename "$f" .gz); done
# 1 行 = 1 フロップの JSON を out/quality.jsonl に追記（計算済みのフロップは飛ばすので、途中で止めても続きから再開できる）
nice -n 19 ./target/release/measure_exploit --postflop ../web/public/postflop \
  --pre out/pre/cash6max-100bb --out out/quality.jsonl --threads 2 --scenario srp-btn-bb,3bp-btn-bb,srp-co-bb
# 下の表と要約（§5・§6）はこの出力をそのまま貼ったもの。手で書き換えない
./target/release/measure_exploit --report out/quality.jsonl
```

- `--split` を付けると、ターンだけ / リバーだけを全カードにした値も出す（表の「ターンだけ」「リバーだけ」の列）。
- 所要時間（4 コアの機械、`nice -n 19`、2 スレッド並列、ほかの作業と同居）: 1 フロップあたり解き直し約 7 分 + 全カードの最適応答（3 回の走査: 今の値・OOP の最適応答・IP の最適応答）約 1 分 = **1 フロップ 462〜605 秒（中央値約 8 分、1 スレッド）**。`srp-btn-bb` の 21 フロップで 5,460 秒 ≒ 91 分（壁時計、2 スレッド）。`srp-co-bb` は 1 フロップ 468〜551 秒、`3bp-btn-bb`（木が小さい）は 323〜446 秒。63 フロップの合計は 29,234 秒（1 スレッド換算、§5 の要約）。メモリは 2 フロップ並列でプロセス全体約 0.65 GB（実測の RSS）（解き直しのソルバーと、5 枚のボードの強さ表 1,176 枚を遅延で作るキャッシュ）。全ランアウトの結果を同時には持たない（再帰で 1 ランアウトずつ足し込む）。
- 正しさのテスト（`cargo test --release measure::`）:
  - `river_file_measure_matches_solver_exploitability`: リバー単独の木を解いて `export` で書き出し、読み直した戦略で測った値が、同じ戦略での `Solver::exploitability` と一致（許容誤差: 1e-4 % + 相対 1e-4）。
  - `all_cards_tree_turn_matches_in_sample` / `all_cards_tree_flop_matches_in_sample`: 全カードをサンプルにした木（ターンから / フロップから。フロップのオールインは全 1,176 ランアウト）で、全カードの値がサンプル内の値（`Solver::exploitability`）と一致。
  - `sampled_deal_matches_solver_on_a_sampled_tree`: サンプルの木で「サンプルだけ配る」と `Solver::exploitability` と一致し、全カードにすると値が大きくなる。
  - `passive_strategy_is_exploitable`: 常にチェック・コールの戦略はポットの 50% 以上搾取される。
  - `ip_range_without_the_check_line_in_the_file`: OOP が必ずベットする（ルートを固定した）リバーの木では、チェックの後の IP のノードがファイルに無い。それでも開始時のレンジが読め（ソルバーの開始レンジをファイルと同じく量子化したものと一致）、測った値が `Solver::exploitability` と一致する（§2）。
  - `board_perm_*` / `assignment_*`: 置換が生きたカードどうしの 1 対 1 対応になること、割り当て規則の具体例。

## 6. 読み方の注意

- **全カードの値は、63 フロップすべてでサンプル内の値の 75〜501 倍。** 「サンプル内 0.1〜0.9%」は、サンプルした 12 通りのランアウトだけを配るゲームの中での誤差で、実際の配り方での誤差ではなかった。目標の 0.3% 以下に入るフロップは 0 / 63（全カードの値は最小 37.5%、最大 198.4%、平均 101.9%）。
- シナリオの間の差（`3bp-btn-bb` の平均 60.3% は `srp` の 2 つの約半分）は、初期ポット（22.5bb と 5.5bb）や SPR が違うので、そのまま「解の良し悪し」の差とは読まない。
- 大きさの大半がどこから来るかは「ターンだけ / リバーだけ全カード」で見る。§5 の 63 フロップは `--split` なしで測ったので列は「—」。別に As7d2c（`srp-btn-bb` #0）だけ測った値（`--flops 0 --split` と `--flops 0 --assign stratum` を別の出力に流したもの。表には入れていない）:

  | As7d2c | ポット比 |
  |---|---:|
  | サンプル内 | 0.482% |
  | ターンだけ全カード（リバーはサンプル） | 38.447% |
  | リバーだけ全カード（ターンはサンプル） | 48.234% |
  | 両方全カード（`Nearest`、表の値） | 75.524% |
  | 両方全カード（`--assign stratum`） | 82.817% |

  ターンとリバーのどちらか一方だけでも数十 % になる。割り当てを層の規則にすると約 7 ポイント悪く、規則の違いは全体の大きさに比べて小さい。推測: リバーは 1 ターンあたり 2 枚しかサンプルが無いので、48 枚のうち 46 枚では「別のリバーでの戦略」を使うことになり、ストレート・フラッシュ・ペアの完成が戦略に反映されない。リバーはポットが大きい（初期ポット 5.5bb に対して数十 bb）ので、初期ポット比にすると大きな値になる。
- 言えること: 今の出荷データ（12 ランアウトのサンプル + この割り当て規則）を全カードで使うと、2 人の最適応答の利得の和が初期ポットの約 1.2 倍（`srp-btn-bb` の平均 120.8%、最小 49.6%、最大 198.4%）になる。和で約 6.6bb、2 人で割ると 1 人・1 ハンドあたり約 3.3bb（初期ポット 5.5bb）。画面の「近似」表示（`ApproxNote`）を外せる水準からは遠い。
- 言えないこと: 「サンプル方式で解いた解を、賢く割り当てたらどこまで下がるか」（割り当て規則の改善の余地）、ベットサイズの抽象化による誤差、プリフロップ（EQR）の誤差。
- 比較に使うとき: 同じ規則（`Nearest`）・同じ定義で測った値どうしを比べる。ステップ 3-3（全カードで解く、またはリバーを端末で解く）では、割り当てが不要になる（サンプル = 全カード）ので、この物差しがそのまま使える。

## 7. 未計測の範囲

- 出荷している 3 シナリオ × 21 フロップ = 63 フロップをすべて計測した（63 / 63）。未計測のフロップは無い。
- 計測していないもの: ターンだけ / リバーだけの内訳（`--split`）と、層の規則（`--assign stratum`）は As7d2c（`srp-btn-bb` #0）だけ（§6）。ベットサイズの抽象化による誤差とプリフロップ（EQR）の誤差は、この物差しの範囲外（§1・§6）。
- 計測は 2 回に分かれた: 61 フロップを先に測り、`3bp-btn-bb` #18・#19 は開始レンジの読み方を直してから測った（§2）。直した前後で、チェックの後のノードがあるフロップの値は変わらない。
