# 08. ポストフロップ解のモデルと既知の限界

> プリフロップと同様、**商用ソルバーの出力ではなく、自作ソルバーが下の抽象化されたゲームで求めた解**です。
> ターン・リバーは代表カードのサンプルで近似しているため、頻度の細部は完全解と異なります。

## 1. ゲーム
- **ヘッズアップ**（OOP=先に動く、IP=後に動く）。フロップ→ターン→リバーを通して解く。
- 開始時のポットとスタックはシナリオで決まる。ポットは**誰のものでもない**として扱い、利得は「最終ポットの取り分 − ポストフロップで入れたチップ」（2人合計は常にポット額＝定和ゲーム）。EV表示はこの定義（初期ポットの取り分を含む）。
- レンジはプリフロップ解（`docs/07`）から切り出す: `ハンドクラスの重み × そのアクションの頻度` を1,326コンボに展開（同じクラスの全コンボが同じ重み）。

| シナリオ | OOP | IP | ポット | スタック |
|----------|-----|----|-------|---------|
| `srp-btn-bb` | BB: BTNオープンへのコール(54.4%) | BTN: オープン(47.3%) | 5.5bb | 97.5bb |
| `3bp-btn-bb` | BB: 3ベット(13.2%) | BTN: 3ベットへのコール(26.2%) | 22.5bb | 89bb |

## 2. アクション抽象化
| | フロップ | ターン | リバー |
|---|---|---|---|
| ベット | 33% / 75% ポット | 66% | 50% / 100% |
| レイズ | ベットの3倍 + オールイン | オールインのみ | オールインのみ |

- ベット/レイズが残りスタックの67%以上ならオールインに置き換える。1ストリートのレイズは「ベット→レイズ→オールインの再レイズ」まで。
- フロップのベットサイズを2種類にしたのは、集計レポートで小さいCベットと大きいCベットを見分けるため。

## 3. カード抽象化（サンプル）
- ターンカード6枚、リバーカード2枚（各ターンごとに別の2枚）を**ランク順に並べて層に分け、各層から1枚**を決定的な乱数で選ぶ。
- チャンスノードの重みは `(残りカード数 / サンプル数) / (残りカード数 − 4)`。「全カードを均等に配る」期待値の不偏推定になる。
- 結果として、フロップの戦略は **6×2=12通りのランアウト** に対して最適化される。ランアウトの偏りがそのまま戦略に出る（例: サンプルにフラッシュ完成札が無いと、フラッシュドローの価値が低く出る）。
- ターンのオールインは**全リバーカード**で評価。フロップのオールインは**固定サンプル120通り**のランアウトで評価（厳密ではない）。
- 画面ではサンプル済みのカードだけ選べる（「ターン/リバーは代表カードだけ計算済み」）。

## 4. アルゴリズム（`solver/src/postflop.rs`）
- 2人ゼロサムの**ベクトル形式CFR+**（線形平均）。1ノードで1,326コンボを同時更新。**1,400反復**で、**700反復目に平均を取り直す**（序盤の反復は均衡から遠く、平均を引きずるため）。
- リバーのショーダウン: ハンドを強さ順に並べ、累積和でO(n)。カード除去（相手がボードや自分と同じカードを持てない）は包除原理で厳密に処理。総当たり計算と一致することをテスト。
- EVは「そのハンドで、ノードに到達した条件のもとでの期待値」。分母（到達質量）は終端の利得を1に置き換えた同じ再帰で求める。
- 到達確率が低い（<0.4%）ノードと、レンジ重み<1%のハンドは書き出さない。

## 5. 検証
| テスト | 内容 |
|--------|------|
| `river_clairvoyant_game_matches_theory` | 実カードのリバーで、OOP=ナッツ or エア / IP=ブラフキャッチャー。ブラフ頻度 `b·w_n / (w_a·(P+b))`、IPのコール頻度 `P/(P+b)` が理論値と一致、ナッツは常にベット |
| `showdown_matches_brute_force` | O(n)ショーダウンが総当たりと一致（共有カードの除去を含む） |
| `three_street_solve_converges` | 3ストリートの小さな木で 定和性(v0+v1=ポット) と exploitability < ポットの4% |
| `allin_equity_matches_enumeration` | AA vs KK のフロップ・オールイン・エクイティが全ランアウト列挙に近い |
| Vitest `postflop.data.test.ts` | 出力ファイルの木構造・チップ会計（フォールドEV=投入額）・戦略が分布になっている・主要ラインの均衡性（到達確率別の段階しきい値）・ストリート別のスポット抽出・相手の自動プレイ |

実測（生成時、各フロップ。`index.json` の `stats[*].exploit`）:

| シナリオ | exploitability（ポット比） | 備考 |
|----------|--------------------------|------|
| `srp-btn-bb` | 0.34〜0.94%（平均0.61%） | 21フロップ。1フロップ約5.7分(1スレッド) |
| `3bp-btn-bb` | 0.14〜0.50%（平均0.24%） | 21フロップ。約4分 |
| `srp-co-bb` | 0.31〜0.93%（平均0.62%） | 21フロップ（Phase 8 で追加） |

平均を取り直さず700反復だけの初回生成では、SRPで1.3〜2.4%、3ベットポットの一部ノードで「頻度30%以上のアクションが最善より3bb悪い」箇所が出ていた。1,400反復＋平均の再開始で、**到達確率20%以上のラインでは最大0.23bb、5%以上で最大0.55bb**になった（実験: 同じフロップで 700反復=0.71% → 平均再開始のみ=0.43% → 1,400反復+再開始=0.16%）。

## 6. 既知の限界
1. **サンプルされたターン/リバー**による近似（上記）。完全な解（全49×48カード）ではない。
2. ベットサイズ・レイズサイズは固定の少数。ポットの33%と75%の間のサイズなどは存在しない。
3. 計算済みは **3シナリオ（BTN vs BB のシングルレイズ・3ベットポット、CO vs BB のシングルレイズ）× 21フロップ** のみ（全1,755種のうち代表）。集計レポートはこの範囲の集計。
4. **プリフロップのレンジはプリフロップ近似モデルに依存**（`docs/07`）。
5. **到達確率が低いライン（特に3ベットポットのフロップで5%未満）は収束が粗く**、頻度30%以上で打たれるアクションでも最善とのEV差が最大約2.6bbになる箇所がある（全32フロップの実測）。採点は「頻度10%以上のアクションは最低でも『正解』」とし、EV損失の数字は解の値のまま表示するので、そのようなラインでは「正解なのにEV損失が大きい」表示になりうる。
6. 他のポジション組（SB vs BB、HJ vs BB、BTN vs SB など）は未計算（`gen_postflop` の `SCENARIOS` に1行足せば計算できる）。
7. スート同型は使っていない（1フロップ=1ファイル、約0.22MB）。同型を使えばフロップ数を1,755に近づけられるが、計算量が数十倍になる。

## 7. 再生成
```bash
cd solver
RUSTFLAGS="-C target-cpu=native" cargo run --release --bin gen_postflop -- \
  --pre out/cash6max-100bb --out out/postflop --scenario srp-btn-bb,3bp-btn-bb --flops 16 --iters 1400 --avg-from 0.5   # 約40分(4スレッド)
cd ../web && npm run solutions:pack    # public/postflop/ に gzip で梱包（index.json 含む）
```
`--turn-cards --river-cards --min-reach --iters --avg-from --only-flop --scenario srp-co-bb` などで変更できる。
