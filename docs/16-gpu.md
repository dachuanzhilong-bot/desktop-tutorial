# 16. GPU で学習する（REFACTOR_PLAN 4-6、2026-11-21、設計）

持ち主の依頼「GPU で動けるようにして」への設計です。持ち主の PC（RTX 4060 Ti 8 GB、Ryzen 9 7900X、DDR5 32 GB、WSL2 Ubuntu）で、**Claude を PC の上で動かして作ります**（クラウドの環境には GPU が無く、ここでは作れず試せないため。持ち主の選択）。数字のうち「見込み」と書いたものは実測ではありません。

## 1. 何が速くなるか（見込み）

- 学習の 1 反復の時間は、ノードの 99% 以上を占めるリバーの部分木（1 フロップに約 6.4 万個、各 27 ノード前後）でほぼ決まる（`docs/14` §16）。各部分木は上からの到達だけで独立に解けるので、GPU で一斉に解ける。
- 速さの上限はメモリの帯域で決まる。4060 Ti は 288 GB/s、DDR5（2 チャネル）は約 60〜80 GB/s。1 反復で regret と strategy sum を 1 回ずつ読み書きする（今のサイズで約 15 GB）ので、GPU の 1 反復は 0.05〜0.1 秒が下限の目安。CPU（4-2・4-3 の後、PC で 0.8〜0.9 秒の見込み）の 3〜5 倍。
- **載る大きさ**（VRAM 8 GB のうち、画面と常駐するアプリが使う分を除いた残り。2026-11-22 の `nvidia-smi` では 2.2 GB が使われていて、空きは約 5.8 GB。壁紙・ブラウザ・ゲームのランチャー・チャットのアプリなどを閉じると増える）。1 フロップの SRP、`docs/14` §14 の数え方:

| ベットサイズ | regret + strategy sum（f32） | strategy sum だけ 16 ビット | 両方 16 ビット | 載るか |
|---|---:|---:|---:|---|
| 今（33・75 / 66 / 50・100） | 7.6 GB | 5.7 GB | 3.8 GB | 両方 16 ビットなら載る（strategy sum だけ 16 ビットは、アプリを閉じて空きを 6.5 GB 以上にしたときだけ） |
| 2 サイズずつ | 12.0 GB | 9.0 GB | 6.0 GB | 両方 16 ビットならぎりぎり |
| 計画の 3-4 | 28.7 GB | 21.6 GB | 14.4 GB | 載らない |

- 載らない大きさを、ターンのカードごとに PC のメモリから送って解くと、1 反復の転送が数十 GB になる（4060 Ti は PCIe 4.0 x8、約 13 GB/s）。CPU より遅くなる見込み。**GPU が効くのは、VRAM に載る大きさの量産だけ**: 今のサイズの作り直し（レーキあり・他の深度）、3-5（シナリオを増やす）を今のサイズか 2 サイズで回すとき。計画の 3-4 のサイズの量産には効かない。

## 2. 作り方

- **外部 crate は足さない**（`docs/04` の方針）。CUDA の部分は `solver/cuda/*.cu` に書き、Cargo の feature `cuda`（既定は無効）のときだけ `build.rs` が `nvcc` でビルドしてリンクする。Rust 側は `src/gpu.rs`（`#[cfg(feature = "cuda")]`、`extern "C"` の宣言とメモリの持ち主の管理だけ）。CI・WASM・feature なしのビルドは今のまま。
- **GPU がするのは、学習の走査のリバーの部分木だけ**（`river::train_subtree` と同じ計算。`sim-cfr+`・`alt-cfr+`・`alt-dcfr` の 3 方式）。フロップ・ターンの段、評価・最適応答（G1 の測定）、書き出しは CPU のまま。
- 呼び出しの単位: 最初は、リバーのカードを配るチャンスノード 1 つ分（48 個の部分木）を 1 回でまとめて解く（今の走査にそのまま差し込める）。呼び出し回数（1 走査に約 1,300 回）が重ければ、ターンのカードごとの部分木の中のチャンスノードを全部まとめる（ターンの段を「上から到達 → GPU → 下から値」の 2 段に分ける）。
- 部分木 1 つ = スレッドブロック 1 つ。台の要素（600 前後の手）をスレッドで分ける。中身は、regret matching、到達、fold（相手の台の上の質量の合計と、52 枚のカードごとの和）、showdown（強さ順の累積和。52 枚のカードごとのブロック内の prefix scan）、値と regret・strategy sum の更新。
- 置き場: リバーの regret と strategy sum は VRAM に置いたままにする（毎回は送らない）。CPU は部分木の根の到達（両者、台の幅）を送り、根の値を受け取る。1 反復の転送は数百 MB の見込み。途中保存と G1 の測定のときだけ、VRAM から CPU に写す。
- 数の表し方: 載せるため、strategy sum（必要なら regret も）を 16 ビット + 手ごとの倍率で持つ（4-4 と同じ考え方）。

## 3. 確かめ方（CPU とビット単位では一致しない）

GPU は足す順番が CPU と違うので、ビット一致はしない。代わりに次で確かめる。

1. **1 反復の差**: 同じ状態から 1 反復した後の regret の差が、f32 の丸め程度（相対 1e-5 以内。16 ビットの所はその精度）。
2. **小さな木で G1**: 49×2 の木で、同じ反復数の後の G1 が CPU とほぼ同じ（差 0.02 ポイント以内）。
3. **本番の木**: As7d2c・49×48 を GPU で G1 0.5% まで解き、反復数・時間・G1 を CPU と比べる。書き出した解で G2'（`docs/14` §11-9）を測る。

量産の物差し（G1・G2'）は CPU の道具で測るので、GPU の計算の誤りは G1 の値に出る。

## 4. 手順（PC の Claude が順に行う）

1. **準備**: WSL で `nvidia-smi` が動くか（Windows 側の NVIDIA ドライバーが WSL の CUDA に対応しているか）。CUDA Toolkit（`nvcc`）を WSL に入れる。
   - 2026-11-22 に確かめた: WSL で `nvidia-smi` が動く。RTX 4060 Ti、ドライバー 621.24、CUDA 13.5 まで対応、使用中 2.2 GB / 8 GB。
   - Toolkit は WSL-Ubuntu 用のもの（ドライバーを含まない `cuda-toolkit-*`）を入れる。WSL の中に Linux 用のドライバーを入れない（Windows 側のドライバーを使う）。
   - この GPU は画面も映している（WDDM）。1 回のカーネルが約 2 秒を超えると、Windows が GPU をリセットする（TDR）。1 回の呼び出しは短く保つ（§2 の単位なら数ミリ秒の見込み）。
2. **計測だけの試作**: 実際の到達でリバーの部分木 1 万個前後を、GPU と CPU（`train_subtree`）で解き、時間を比べる（`solver/cuda/bench_river.cu` と `solver/src/bin/bench_gpu.rs`）。**3 倍に届かなければ、ここで止めて報告する。**
3. **組み込み**: `--features cuda` と `gen_postflop --device gpu`。§3 の 1・2 で確かめる。
4. **本番の木**: §3 の 3。63 フロップの量産を GPU で回したときの時間を見積もり、`docs/14` に書く。

`pc.sh` の測定（4-1・4-3）を流している間は、CPU の時間の比べ方が乱れるので、CPU との速さの比較はその後にする。

## 5. 手順 1・2 の結果（2026-11-22、PC。`pc.sh` が G2' を測っている間）

### 5-1. 手順 1: CUDA Toolkit

- WSL の `sudo` はパスワードが要るので、apt ではなく NVIDIA の redist（`developer.download.nvidia.com/compute/cuda/redist/`、SHA-256 を照合）から **13.3.1** の `cuda_nvcc`・`cuda_cudart`・`cccl`・`cuda_crt`・`libnvvm`・`cuda_culibos` だけを `~/cuda-13.3` に展開した（`~/cuda` はそこへのリンク、`lib64 → lib`）。WSL-Ubuntu 用の apt リポジトリの最新と同じ版。ドライバーは入れていない（Windows 側の 621.24 / CUDA 13.5 を使う）。gcc 15.2 で通り、RTX 4060 Ti（sm_89、34 SM、L2 32 MB）でカーネルが動いた。
- ビルド: `cd solver && CUDA_PATH=$HOME/cuda cargo build --release --features cuda --bin bench_gpu`。feature なしでは `build.rs` は何もしない（CI・WASM は今のまま）。

### 5-2. 手順 2: 計測だけの試作

- 道具: `solver/cuda/bench_river.cu`（カーネル）、`solver/src/gpu_bench.rs`（並べ替えと CPU 側）、`solver/src/bin/bench_gpu.rs`。`Solver::capture_river_inputs` が、1 反復の中で各リバー部分木に入る到達を記録する（反復の結果は変わらない）。
- 測り方: As7d2c・`srp-btn-bb`・**49×8**（リバー部分木 10,584 個）・`alt-dcfr`。3 反復の後の到達で、同じ状態から GPU と CPU（`river::train_subtree`）が同じ 1 反復（2 走査）をして差を見て、続けて 5 反復の時間を測る。49×48 の換算は部分木の数に比例（×6）。

| | 1 反復 | 49×48 の換算 |
|---|---:|---:|
| GPU、相手の手の和を f32 | **30.6 ms** | **0.18 s** |
| GPU、相手の手の和を f64 | 75.4 ms | 0.45 s |
| CPU 1 スレッド（`pc.sh` と同時） | 2.41 s | 14.5 s |
| CPU 4 スレッド（`pc.sh` と同時） | 0.64 s | 3.85 s |
| 参考: 49×48・24 スレッドの 1 反復全体（4-3 の PC 測定、リバー以外も含む） | | 0.66 s |

- 1 反復の差（ノードごとの最大の差 / そのノードの最大の絶対値、の最大）: f32 で regret 1.5e-4、strategy sum 0、根の値 6.3e-6。**f64 ではビット一致**（regret・strategy sum・根の値すべて。49×2 でも同じ）。
- メモリ: bench のピーク RSS 3.0 GB。VRAM はアップロード後の空きが 5.9 GB（1.26 GB を置いた）。1 回のカーネルは 15 ms 前後で、TDR（約 2 秒）から遠い。

### 5-3. 読み方と、まだ決まっていないこと

- **3 倍の判定はまだ。** 比べるべき CPU の数字は「24 スレッドでリバー部分木だけ」で、`pc.sh` が CPU を使っている間は測れない（§4 の最後）。今ある数字では、0.66 s（1 反復全体）/ 0.18 s = 3.6 倍。全体にはリバー以外（フロップのオールインのランアウトなど）も含まれるので、リバーだけと比べると下がる。リバーの CPU 時間が 0.55 s 以上なら 3 倍に届く。`pc.sh` の後に `bench_gpu --pre <pre> --river-cards 8 --solve-threads 24 --cpu-threads 24` で測って決める。
- **GPU にしても CPU に残る分**: 49×8・4 スレッドで、1 反復全体 1.01 s のうちリバー部分木は 0.64 s、残りは 0.37 s。49×48・24 スレッドで残りがどれだけかは、手順 4 の全体の時間に効く（残りが 0.15 s なら、全体は 0.66 → 0.33 s で 2 倍止まり）。手順 3 に進むなら、ここも測る。
- **精度**: f32 の和では regret の差が §3-1 の目安（1e-5）を超える。差は、値の和（相手の 600〜1,000 手）の f32 の丸めが、regret の `y - x` の引き算で目立つもの。f64 の和なら CPU とビット一致するが 2.5 倍遅く（0.45 s）、3 倍に届かない。手順 3 では f32 で進め、§3-2（49×2 で G1 の差 0.02 ポイント以内）で判定するのがよいと考える（持ち主か上位モデルの確認がほしい）。

### 5-4. 試作の中で速くしたこと（49×2 の 1 反復）

| 変更 | ms |
|---|---:|
| 最初の版（部分木 1 つ = 256 スレッドのブロック 1 つ、全ノードの到達と値をブロックの作業域に持つ） | 12.2 |
| ノードの表を shared memory に、手の数ごとの展開、fold と showdown を warp 単位の和に | 10.4 |
| **深さ優先に歩き、作業域の枠を使い回す**（作業域 31 MB → 9.6 MB で L2 に収まる） | **7.7** |

- 効かなかったもの: SM あたりのブロックを増やす（作業域が L2 からあふれて遅くなる）、128 スレッドのブロック。
- 帯域の下限: 49×8 の 1 反復で約 3.8 GB を読み書きする（regret を 2 回読んで 1 回書く、strategy sum を読んで書く）。288 GB/s で 13 ms。今は 30.6 ms（下限の 43%）。残りの案: 更新する側の戦略を DOWN から UP まで作業域に持つ（regret の読みを 1 回減らす、約 −17%）、strategy sum を 16 ビット（§2 の VRAM のため。約 −17%）。
