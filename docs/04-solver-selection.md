# 04. ソルバーの選定と理由

## 結論
**依存ライブラリなし(Rust標準ライブラリのみ)の自作CFR+ソルバー**を採用する。
場所: `solver/`（MITライセンス想定）。事前計算はネイティブで実行し、Phase 4のSolveではそのままWebAssemblyにビルドする。

## 比較

| 候補 | ライセンス | 言語 | 状態 | 評価 |
|------|-----------|------|------|------|
| `b-inary/postflop-solver` | **AGPL-3.0-or-later**（Cargo.tomlで確認） | Rust | 2023-10に開発停止（READMEに明記） | 高速で高品質。ただしAGPL |
| `bupticybee/TexasSolver` | **AGPL-3.0**（LICENSEで確認） | C++ | — | AGPL。WASM化は追加作業が大きい |
| 自作 CFR+ | 自由（MIT想定） | Rust | 本リポジトリ | 速度は劣るが、制約なし・WASM化容易・解釈しやすい |

### なぜAGPLを避けるか
- **AGPL-3.0 は「ネットワーク越しにユーザーへ提供する場合」にも対応ソースの提供を求める**。WASMをブラウザに配信するアプリは、ライブラリを同梱した時点でアプリ全体のソース公開義務が及ぶと解釈されるのが一般的。
- Supabaseの認証・同期、将来の有料機能など、事業の選択肢を狭めない。
- 他社ツール互換を目的とした派生にならないよう、コードも解データも完全オリジナルにする。

### この環境での実務的な制約（実測）
- `static.crates.io`（crateのダウンロード）と `github.com` の clone/zip は**ネットワークポリシーで遮断**されている（HTTP 403を確認）。`raw.githubusercontent.com` と npm・PyPIは到達可。
- そのため postflop-solver は依存（`rayon`,`bincode`,`regex`,`once_cell`,`zstd`）ごと取得・ビルドできない。
- 自作は依存ゼロなので、制限下でもビルド・テストが完結する。

## 自作ソルバーの設計 (`solver/src/engine.rs`)
- **ベクトル形式のCFR+**（線形平均）。各プレイヤーのレンジを「ハンドクラスごとの到達確率ベクトル」で持ち、1ノードで全ハンドを同時に更新する。
- **nプレイヤー対応**（プリフロップ6人）。カードの重なり(ブロッカー)は 169×169 の厳密な組合せ数から計算した行列 `P_q[a][b]` で扱う。
- 終端: フォールド決着 / ヘッズアップ・ショーダウン / **3人ショーダウン**（各ペアのヘッズアップ取り分の平均 `S_i=(s_ij+s_ik)/3`。ゼロサム保存）。行列×ベクトル2〜6回で評価できる。
- **ロジットのトレンブル**（学習中のみ）: 到達確率ゼロの枝（例: 誰もフラットしない局面のスクイーズ）が未学習のまま「全員スクイーズ」になる退化均衡を避けるため、EVに比例した微小なランダム化を入れ、最後に切って平均を取り直す（`explore`, `reset_average`）。詳細は `07-preflop-model.md`。
- 速度: プリフロップ6-max(約6,300決定ノード)で **1反復 約0.12秒**（1スレッド）。

## Phase 3: ポストフロップ（実装済み, `solver/src/postflop.rs`）
- 同じベクトル形式CFR+を、**1,326コンボ・フロップ→ターン→リバー**の2人ゼロサムに拡張。リバーのショーダウンは強さ順ソート+累積和でO(n)（カード除去は包除原理で厳密）。
- ターン/リバーは**層化サンプル**したカードで近似（モデルの詳細・限界は `08-postflop-model.md`）。
- 1フロップ ≈ 9,300ノード（3ベットポットは4,800）、1反復 ≈ 0.25秒。1,400反復（途中で平均を取り直す）で exploitability ≈ ポットの0.2〜0.8%。4スレッドで 2シナリオ×16フロップ ≈ 40分。
- テスト: 実カードのリバー・クレアボヤントゲームの理論値、O(n)ショーダウン=総当たり、3ストリート木の定和性とexploitability、オールインのエクイティ。

## Phase 4 の方針
- **WASM**: `wasm32-unknown-unknown` ターゲットに C ABI（`extern "C"`）で公開し、`wasm-bindgen` なしの薄いJSグルーで呼ぶ（crate取得不要）。WASM threads/SharedArrayBufferが使えない環境では単スレッド。
- **Solve**: ユーザーが指定するボード・レンジ・スタック・ベットサイズでその場で計算。完全な3ストリート解はメモリが大きいので、まずはサンプル抽象化のまま、ターン・リバー指定の「サブゲーム」(ボード4〜5枚)を速く解く経路から始める（`build_tree` は4/5枚のボードにも対応済み）。
- **ノードロック**: ある決定ノードの戦略を固定し（`regret` を更新しない）、他方の最適対応を計算。
- **将来 postflop-solver を使いたくなった場合**: ソルバー部分を別プロセス/別サービスに分離し、アプリ全体をAGPLで公開する選択でのみ可能。その判断はプロダクト側の事業判断として別途行う。
