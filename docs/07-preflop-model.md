# 07. プリフロップ解の近似モデルと、既知の限界

> **この解は「商用ソルバーの出力」ではありません。** 自作ソルバーが、下の近似モデルの上で求めた**そのモデルでの均衡**です。
> 学習用の目安として十分な形（オープン幅・3ベット・スクイーズなど）になるよう検証していますが、細部の頻度は商用ツールと一致しません。画面にも「近似モデル」と表示しています。

### 多人数ポットの扱い（近似）
- 単独レイズポット（オープンに対する対応）では **最大3人** がフロップを見られる（フラット+オーバーコール）。
- 3ベット以降は **ヘッズアップのみ**（3ベットへのコールは1人まで）。4人以上のポットは存在しない。
- 3人ポットの取り分は各ペアのヘッズアップ取り分の平均 `S_i = (s_ij + s_ik)/3`（ゼロサムを保つ。実際の3人エクイティではない）。

## 2. 終端の価値（エクイティ実現モデル, EQR）
- **オールイン**: 169×169の生エクイティ表（モンテカルロ、1ペアあたり60,000サンプル、5枚ボード、カード除去対応）をそのまま使用。AA–KK=81.9%、AKs–22=50.2%、AKo–QQ=43% などの既知値と一致することをテスト。
- **フロップに進む場合**: ポストフロップは解かず、ハンドのエクイティ `e` に **実現率 R** を掛けて取り分を決める。

```
share_IP = e·R_IP / ( e·R_IP + (1−e)·R_OOP )          （ゼロサム）
payoff   = pot · share − 自分の投入額
R_role(hand) = 1 + k(SPR) · ( mean_role + slope_role · (play(hand) − 0.5) )
k(SPR)   = 1 − exp(−SPR / 3.5)          （SPRが小さいほど実現率は1に近づく）
play(hand) = ペア/スーテッド/連続度/ハイカードから作る 0〜1 の遊びやすさ指標
IP : mean=+0.10, slope=0.25      OOP: mean=−0.22, slope=0.32
```
- パラメータは「各席のオープン幅・BBのディフェンス幅が公開されている一般的な水準(UTG≈16%, CO≈27%, BTN≈45%前後)に入る」ことを基準に手で調整。**フロップ解を持たないための代用**であり、Phase 3 でフロップの実解から求めた値に置き換える。
- 画面の「EQR」欄は、このモデルが仮定した R の値（実測ではない）。

### 実解から求めた EQR（REFACTOR_PLAN 3-1。道具と実験の結果。**出荷データはまだ上の手作りのモデル**）

フロップの実解から R を求める道具を作り、プリフロップ → フロップ → 表 → プリフロップ…と回した。結論は先に書く: **道具は動くが、周回が 0.5 ポイント未満に収まらず、出てきた解は BB のディフェンスが広すぎる**（下の §4 の表）。そのため出荷データは差し替えていない（持ち主の決定、2026-11-17。理由は下の「結果」）。

**道具**
- `gen_eqr`（`solver/src/bin/gen_eqr.rs`、本体は `solver/src/eqr.rs`）: 解いたフロップ（`TSP1`）のルートから、ハンドクラス別・IP/OOP 別の「実現した取り分」を測り、表にする。表は 役割（OOP / IP）× **アグレッサーか（コーラー / アグレッサー）** × 169 クラスの `m` で、`R = 1 + k(SPR)·m`（`k` は上の式のまま）。形式は `solver/data/eqr-loop7.tsv`（周回の最後の表）。
- `gen_preflop --eqr FILE`: その表でプリフロップを解く。`--eqr` なしは従来のパラメータ式で、**出力は 1 バイトも変わらない**（`main` と本ブランチを同じ設定で解いて、出力ディレクトリを `diff` で確かめた。表が手作りの値と同じなら終端の値もビット単位で同じになるテストもある）。

**測り方**
1. ルートの価値: OOP は最初に動くのでルートの値、IP は OOP の各行動の確率で重み付けた子ノードの値。2 人の合計がポットになること（ゼロサム）を、全フロップで確かめる（ずれはポットの 2% 以内。ファイルの量子化と、枝刈りした到達確率の小さいラインのため 0 にはならない）。
2. 取り分 `s = 価値 ÷ 初期ポット`。ポストフロップの利得は「最終ポットの取り分 − フロップ以降の投入」なので、強い手は `s` が 1 を超える。
3. プリフロップのモデル自身の式 `share = e·R_IP / (e·R_IP + (1−e)·R_OOP)` を通して、測った取り分を再現する R を求める（`calibrate`）。この式は R を全体に何倍しても値が変わらないので、水準は「平均の分母 = 1」に固定する。生エクイティとの単純な比 `s/e` をそのまま R にするより、モデルに戻したときの誤差が小さい（下の表）。
4. データの薄いクラスは、近い強さの同じ種類（ペア / スーテッド / オフスート）のクラスの値へ寄せ、データに無いクラスは、観測されたクラスの平均を取る（外へ延ばさない。外挿は 72o が R=2.5 になって壊れた）。

**計画からの変更（持ち主の確認待ち）**: 計画の軸は「ハンドクラス・IP/OOP・SPR」。測ってみると、同じ IP でも SRP のアグレッサーと 3 ベットポットのコーラーで平均の `m` が大きく違った（169 クラスの単純平均で、IP: アグレッサー +0.11 / コーラー −0.12、OOP: アグレッサー −0.48 / コーラー −0.17。`eqr-loop7.tsv`）ので、役割だけの表では 3 ベットポットが合わない。そこで「そのポットのアグレッサーか」の軸を足した。SPR は SRP の 17.7 と 3 ベットポットの 4.0 の 2 点でしか測っておらず、`k(SPR)` の形は検証していない。

**モデルの誤差**（測った取り分とモデルの差。クラス加重の rms。周回 5 のフロップ。IP / OOP）

| シナリオ（フロップ 21 個） | 手作りの式 | 比 `s/e` | 測った取り分を再現する R（`calibrate`。OOP 側は 0 に合わせてある） | 表（薄いクラスを寄せたあと） |
|---|---|---|---|---|
| SRP BTN-BB（SPR 17.7） | 0.091 / 0.076 | 0.068 / 0.039 | 0.028 / 0.000 | 0.039 / 0.026 |
| SRP CO-BB | 0.085 / 0.074 | 0.063 / 0.039 | 0.022 / 0.000 | 0.032 / 0.025 |
| 3 ベットポット BTN-BB（SPR 4.0） | 0.088 / 0.089 | 0.052 / 0.064 | 0.007 / 0.023 | 0.027 / 0.033 |

平均の水準は手作りと合っている（SRP BTN-BB の OOP: 測った `s/e` 0.83、手作りの平均 R 0.79。IP: 1.13 と 1.14）。差が出ていたのはクラスごとの形（取り分の誤差が 0.08〜0.09 から 0.03 前後に下がる）。

### レーキ（REFACTOR_PLAN 3-2。`gen_preflop --rake-pct x --rake-cap y`）
- 「ポットの x%、上限 y bb、フロップを見なければ 0」。全員フォールドで終わる終端は 0。フロップへ進む終端（ヘッズアップ・3 人の EQR 終端、オールイン）は、その時点のポット（降りた人の投入額を含む）から取る: `payoff = (pot − rake)·share − 自分の投入額`。2 人（3 人）の受け取りの合計 = ポット − レーキ。
- **近似**: 実際のレーキはフロップ以降のベットで大きくなった最終ポットから取られるが、このモデルはフロップに入る時点のポットで計算する（ポストフロップを解かないため）。上限 y があるので、大きなポットほど差は小さい。EQR の係数はレーキなしで調整したまま。
- 解 ID に付く（`cash6max-100bb-r5c3`、`docs/03`）。`x = 0`（既定）はレーキなしで、出力は 3-2 より前と 1 バイトも変わらない。
- 2 人ゲームでもレーキがあると定和でなくなるので、CFR の均衡への収束は理論上の保証の外になる（多人数と同じく、実際の収束は best-response gain で確かめる）。

## 3. 解法
- ベクトル形式 CFR+（線形平均）、1反復≈0.12秒。**学習2,000反復 + 仕上げ4,000反復**（書き出す平均戦略は仕上げ分のみ）。
- 6人ゼロサムではないため **ナッシュ保証はない**。収束の指標は「各プレイヤーが他全員の平均戦略に対して単独で戦略を変えたときの最大の得」(best-response gain) で、最終値は **最大 0.0002bb / 平均 0.0001bb**（`manifest.json` の `info.brGainMax`）。
- **ロジットのトレンブル**: 到達確率ゼロの枝は学習されず「全員スクイーズ」のような退化した応答になり、その応答に対してフラットのEVが−16bbと評価されて、誰もフラットしなくなった（実際に発生）。学習中だけ全アクションに EV に比例した微小な確率(総計20%, λ=3)を割り当て、最後にトレンブルを切って4,000反復で平均を取り直した。結果、BTNのUTGオープンへのフラットが約9%出る。

（「SB レイズ」は SB の 3bb レイズ。SB はほとんどリンプする。「BB 対…」はフォールド以外の割合。各周回の解は、前の周回の表で解いたプリフロップ解でフロップ 63 個（3 シナリオ × 21）を 700 反復で解いて作った表から。best-response gain は周回 7 が最大 0.0006bb / 平均 0.0003bb、レーキありが 0.0008 / 0.0004（出荷は 0.0002 / 0.0001）。）

**止める条件（レンジ幅の変化が 0.5 ポイント未満）には届かなかった。**
- 表を毎周そのまま差し替えると、周回 1 → 4 は 2 周期で振れた（UTG 15.8 → 11.5 → 13.8、BB 対 UTG 45.9 → 27.2 → 40.8）。周回の間の表の差が大きく（IP の `m` の rms 0.5）、クラス別の値が、そのときのレンジに入っている手に引きずられる（レンジに入る手は実現が良く見える、という選択バイアス）。
- 3 周分の表の平均で減衰させると、表の差は rms 0.06〜0.25 に縮み、UTG・HJ・CO は周回ごとの変化が 0.3 ポイント以内に収まった。だが BTN は ±2.5 ポイント、BB のディフェンスは 2〜8 ポイント動き続けている（BB の対 BTN は 81〜95%。無差別に近い手が多く、少しの R の違いで大きく動く）。

**出荷しない理由**: 周回 5 以降の解は、手作りより UTG・HJ・CO が 3〜4 ポイント狭く、**BB が対 BTN で 87〜93% を守り**（手作りは 67.6% で、§6 の 1 で「広め」と書いた水準よりさらに広い）、SB はほぼリンプだけ（90%）になる。手作りのほうが、§2 で目安にした水準（UTG≈16%・CO≈27%・BTN≈45%）に近い。レーキ（5% / 上限 3bb）を足すと BB 対 BTN は 81%、BTN は 40.8% に下がるが、UTG は 13.6% のまま。
- 原因は未確定。考えられるもの: (1) 測ったフロップ解は**サンプル解**（全カードで測ると exploitability が 100% 台。`docs/14` §6）で、その R が全カード解と同じかは未確認（REFACTOR_PLAN 3-1 の「3 フロップで確かめる」。全カードのフロップ解は 3-3-7 の量産まで無いので未実施）。(2) 測ったシナリオは 3 つ（SRP の BTN-BB と CO-BB、3 ベットポット BTN-BB）だけで、SB やスクイーズ、UTG・HJ のオープンは、近いシナリオの値を借りている。(3) SPR を 2 点でしか測っておらず、`k(SPR)` の形は仮定のまま。(4) レーキ・多人数・4 ベット以降は表に入っていない。

## 6. 既知の限界（正直な一覧）
1. **商用ソルバーと一致しない**。特に SB はリンプ58%・レイズ10%とリンプ寄り（BBがポジションを持つため、このモデルではレイズが不利）。BBのディフェンスは広め（対BTN 67.6%）。
2. ポストフロップ未解決。EQRはモデル値。ボードやラインに応じたリアライゼーションの差は出ない。
3. 4人以上のポット、コールドコールの3ベット/4ベット、複数サイズ（ミニレイズ・複数の3ベット額）は未対応。
4. 3人ポットの取り分は近似（上記）。
5. 到達確率が低いライン（<1%）は収束が粗い（無差別になるべき頻度のEV差が最大0.14bb）。採点は「頻度10%以上のアクションは最低でも"正解"」とすることで影響を和らげている。
6. 非コンテスト側のカード除去（ヘッズアップ決着時の他の席のブロッカー）は無視。
7. HU、9-max は未生成。20/40/60/200bb は **Phase 7 で生成済み**（下の「スタック深度」。**100bbほど調整・検証していない**）。
8. レーキありの解（REFACTOR_PLAN 3-2）は、レーキをフロップに入る時点のポットで取る近似（上の「レーキ」）。出荷データはまだレーキなしだけ。
9. 実解から求めた EQR（REFACTOR_PLAN 3-1。上の §2・§4）は、道具と実験の結果だけで、**出荷データには使っていない**。手作りの係数は、公開されている水準に合わせて手で調整したままで、レンジ幅の目安と食い違うときは手作りのほうを正とする。

## 7. スタック深度（Phase 7）

`gen_preflop --stack <bb>` で、20 / 40 / 60 / 100 / 200bb の6-max解を作った（ID は `cash6max-<bb>bb`）。ツリーのサイズ規則は共通（オープン2.5・SB3・BBアイソ4、3ベット IP 3× / OOP 3×+3.5、4ベットは2.3×で、スタックの40%以上ならジャム、5ベットはジャム）。

**短いスタックの追加**: 同じ規則のままだと、20〜40bbで「3ベットのジャム」や「オープンのジャム」という選択肢が無く、誰も3ベットしないので UTG が32%もオープンする（100bbは15.8%）ことが分かった。そこで、**20bb以下では通常のオープンに加えてオープンジャム、45bb以下では通常の3ベットに加えてリジャム**（先にフラットした人がいない場合）を選べるようにした（`open_jam_max=25`, `shove_3bet_max=45`）。ジャムには1人しかコールできない（3人オールインは扱わない）。

| 40bb | 21.5% | 38.2% | 42.5% | |
| 60bb | 15.2% | 47.9% | 66.3% | ジャム選択肢なし |
| 100bb | 15.8% | 47.3% | 65.7% | 従来 |
| 200bb | 15.1% | 50.0% | 66.4% | ジャム選択肢なし。4ベットの後に5ベットジャム |

各深度の best-response gain（最大）: 20bb 0.0011 / 40bb 0.0012 / 60bb 0.0015 / 100bb 0.0002 / 200bb 0.0010 bb。

**限界**: EQR（エクイティ実現率）のパラメーターは100bbで調整したまま。市販ソルバーの20〜40bbと比べると、UTG/HJのオープンが広め・BTNが狭め、SBのリンプが多めになる傾向がありうる（**突き合わせはしていない**）。ポストフロップの解は100bbのみなので、他の深度では通しプレイの「フロップへ進む」は出ない。

## 8. 再生成の手順
```bash
cd solver
RUSTFLAGS="-C target-cpu=native" cargo run --release --bin gen_preflop -- --out out/cash6max-100bb   # 約15分(1スレッド)
cargo run --release --bin gen_preflop -- --stack 40 --out out/cash6max-40bb                          # 他の深度 (20/40/60: 5〜12分, 200: 約25分)
cd ../web && npm run solutions:pack                                                                   # public/solutions/ へ gzip
```
乱数シードは固定(`--seed`)なので、同じバイナリ・同じ引数なら同じデータになる。
EQRパラメータは `--ip-mean --ip-slope --oop-mean --oop-slope --spr-scale`、トレンブルは `--explore --lambda`、仕上げは `--polish` で変更できる。
レーキは `--rake-pct 5 --rake-cap 3`（ID と既定の出力先が `cash6max-100bb-r5c3` になる。`--rake-cap` を省くと上限なしで `-r5`）。
