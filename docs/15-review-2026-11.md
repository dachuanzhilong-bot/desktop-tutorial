# 15. 根本からの見直し（2026-11-21、上位モデルのレビュー）

持ち主の依頼「根本的な所からすべて見直して」への答えです。**実装はしていません**（CLAUDE.md「計画と違うやり方が必要だと思ったら、実装せずに理由を書いて止まる」）。数字はこのコンテナ（4 コア・15 GB）での実測で、「推定」と書いたものは実測ではありません。実験のコードはブランチ `claude/exp-review` に置き、main には入れていません（§7）。

## 1. 結論

**方針は変えません。** 全ターン・全リバーで事前計算し、リバーは端末で解く方式、G1・G2' の物差し、サーバーなしの PWA、自作ソルバー（外部 crate なし）は、どれも正しいままです。63 フロップは G1 ≤ 0.5% を満たしました。

変えるべきなのは、**ソルバーの解き方**と**データの置き場所**と**作業の進め方**です。

1. **ソルバーの更新の仕方（一番大きい）。** いまの CFR+ は、木を 1 回たどるたびに、両者の後悔（regret）を同時に更新しています。CFR+ は本来、片方ずつ交互に更新する方式です。交互にするだけで、同じ計算量での誤差が、ターンの木で 3〜7 分の 1、フロップの木で __FLOP_RATIO__ になりました（§2-1・§2-2）。1 回たどる時間は変わりません。量産の時間は、精度が同じなら __SPEEDUP__ になる見込みです（推定）。
2. **リバーの平均を持たなくてよくなる見込み。** 同時に更新する今の方式では、リバーの「最後の反復の戦略」が 15〜21% と悪いため、リバーの平均（strategy sum）を持っていました。これがメモリの半分です。交互に更新すると、最後の反復でも 0.17〜0.52%（ターンの木）になりました（§2-3）。リバーの平均をやめると、**メモリが半分**になり、計画の 3-4 のサイズ（28.7 GB）も 14.4 GB で持ち主の PC に載ります。G1 の測り方（リバーを平均で測る）が変わるので、持ち主の判断が要ります（§6）。
3. **1 反復の中身も約 2 倍にできる見込み。** 全カードの木のノードの 99% 以上はリバーですが（As7d2c の 1,664,826 ノードのうち約 99.6%。49×2 と 49×8 の木のノード数から推定）、そこは 3-3-4 で速くしたリバー専用の歩き方を使っていません（リバーだけの木にしか使っていない）。1 反復の時間の内訳は、3-3-4 の改善前のリバーとほぼ同じ形でした（§2-4）。3-3-4 では同じ手当てで 2.4 倍速くなっています。
4. **ベットサイズを増やす価値は、ボードによって違う。** ターンの木で、均衡での EV がポットの 0.04〜0.56% 動きました（§2-5）。濡れたボード（Qs Jd 6s 9h）では G1 の目標（0.5%）と同じくらいで、無視できません。一方、計画のサイズは計算が 3.77 倍・メモリ 28.7 GB です。**§3 の高速化（フェーズ 4）を先に入れれば、3-4 と 3-5 の両方が現実的になる**ので、どちらを先にするかは、その後に決めれば足ります。
5. **解データを git の履歴に入れ続ける方式は、3-4・3-5 で行き詰まります。** 作り直すたびに、100 MB から数百 MB が履歴に残り続けます（いまのリポジトリは約 107 MB で、PR #46 をマージすると約 109 MB 増える）。GitHub Pages の公開サイトにも容量の上限があります（GitHub の案内では 1 GB。この環境から公式の説明を開けなかったので、記憶による値。要確認）。3-5 で 1,000 フロップ近くになると、1 フロップ 1.7 MB で 1.7 GB です。データは GitHub の Releases（リリースの添付ファイル）に置き、デプロイと CI がそこから取ってくる形を提案します（§4）。**PR #46 をマージする前に決める**のが一番安くつきます。
6. **作業の進め方。** CI が 1 回の push で 2 本走っています。「1 依頼 1 ステップ」で、持ち主の判断が要らない所でも往復が生まれています。PC の作業が手作業です。文書が長く、毎回読むのに時間がかかります（`docs/14` は 728 行）。§5 に直し方の案を書きました。

### 2-3. リバーの「最後の反復」で測った値（ターンの木）

量産ではリバーの戦略は配らない（端末で解き直す）。事前計算のリバーは、フロップ・ターンを学習させる相手でしかない。そこで、リバーだけ平均ではなく最後の反復（regret matching）にした組の exploitability も測った（`Solver::set_current_strategy_from(2)`）。

| 方式 | 走査数 | 全部平均（今の G1 の定義） | リバーだけ最後の反復 |
|---|---:|---:|---:|
| CFR+ 同時（今） | 1,000 | 0.818 | 20.871 |
| 同 | 2,000 | 0.477 | 14.806 |
| CFR+ 交互 | 1,000 | 0.237 | 0.445 |
| 同 | 2,000 | 0.072 | **0.224** |
| DCFR 交互 | 1,000 | 0.166 | 0.518 |
| 同 | 2,000 | 0.045 | **0.168** |

- 今の方式では、最後の反復は使えない（15〜21%。`docs/14` §13-1 の 9.19% と同じ話）。だからリバーの平均を持っていた（SRP 1 フロップ 7.57 GB のうち 3.77 GB）。
- 交互に更新すると、最後の反復でも 0.5% を下回る。リバーの平均を持たずに「フロップ・ターンは平均、リバーは最後の反復」の組で G1 を測れば、メモリは半分（今のサイズで 3.80 GB、計画の 3-4 のサイズで 14.43 GB。`docs/14` §14-2）。
- この組は、実際に存在する戦略の組なので、その exploitability が 0.5% 以下なら、「配るフロップ・ターンの戦略は、誤差 0.5% 以下の戦略の組の一部」と言える（今の G1 と同じ種類の保証）。端末で解き直したあとの値は、今までどおり G2' で別に測る。

## 4. データの置き場所（提案）

- 今: `web/public/postflop/**/*.bin.gz` を git に入れ、Pages のデプロイはリポジトリの中身をそのまま書き出す。
- 案: 量産の結果を `postflop-v3-<ビルド ID>.tar` として GitHub の Release に添付する。`web/data.lock.json`（Release の名前とハッシュ）だけを git に入れ、`npm run data:fetch` が取ってきて `public/postflop` に展開する（ハッシュを確かめる）。`pages.yml` と `ci.yml` はビルドの前にこれを呼ぶ。
- 良い点: 作り直しても履歴は増えない。PC からの送信も Release への添付 1 つになる（今は 63 ファイルの commit と push）。
- 気をつける点: Pages の公開サイト全体の上限（案内では 1 GB、要確認）は、置き場所を変えても残る。3-5 の規模では、①配るフロップを絞る、②ファイルを小さくする（到達の低いラインを落とす・EV を粗くする）、③データだけ別の静的ホスティング（無料枠のあるオブジェクトストレージ）に置く、のどれかが要る。3-5 の範囲を決めるときに、合わせて決める。
- PR #46 は、この案を採るならデータの commit を Release に置き換えてからマージする。採らないなら、今のままマージしてよい（109 MB は今回 1 回なら問題ない）。
