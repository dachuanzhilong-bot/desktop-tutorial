# 10. Analyze（ハンド履歴）とログイン・クラウド同期

Phase 5 の設計と実装メモ。

## Analyze

```
web/src/lib/analyze/parse.ts       PokerStars テキスト履歴のパーサー
web/src/lib/analyze/normalize.ts   6-max の席(UTG..BB)・bb単位への正規化、フロップ時のポット/スタック
web/src/lib/analyze/match.ts       プリフロップの判断を解のツリーにたどり、EV損失で採点。フロップのレンジ復元
web/src/lib/analyze/aggregate.ts   概要・弱点・練習セット・絞り込み
web/src/app/analyze/page.tsx       取り込み・一覧・弱点・練習セット作成
```

### 取り込める形式
- **PokerStars**、キャッシュゲーム、No-Limit Hold'em（ゾーム含む）。**GGPoker** は同じ書式（ヘッダーが `Poker Hand #HD…`）なので同じコードで読むが、**実ファイルでは確認していない（試験的）**。実マネー/プレイマネー、BOM・CRLF、1ファイルに複数ハンド。
- 対象外（理由つきで一覧に出す）: トーナメント、他のゲーム、ラン・イット・トワイス、ヒーローのカードが無い、ブラインドが無い、7人以上のテーブル、有効スタックが 15〜250bb の外。
- 名前に `: ` や空白を含むプレイヤー、シッティングアウト、`and is all-in`、返却されたアンコールベット、ショーダウンも扱う。
- ハンドIDで重複排除（同じファイルを何度取り込んでも増えない）。結果は IndexedDB（`hands` ストア）に保存し、書き出しJSONにも含める。

### 席の割り当て（`normalize.ts`）
SB・BBをブラインドの支払いから決め、BBの次から時計回りに SB の手前まで並べた最後を BTN とし、そこから逆順に CO, HJ, UTG とする。5人・4人・3人・ヘッズアップも同じ規則（人のいない席は「フォールド済み」として木をたどる）。

### 採点（`match.ts`）
- ヒーローのプリフロップの各判断を、解のツリーにたどって（フォールド／コール＝チェック／レイズ）、練習と同じ `gradeAnswer`（EV損失 → 最善/正解/不正確/ミス/大ミス）で採点する。
- レイズのサイズは解にある**1種類のレイズ**に対応づける（ジャムはオールインがあればそれ）。実際のサイズが解のサイズの 1.35 倍以上/以下なら「近似で採点」と表示する。**サイズが違うので EV損失は目安**（例: 100bbジャムがBTNオープンへの3ベット(約11bb)として採点される）。
- 解にない行動（UTGのリンプなど）や、順番が合わない行は、そこで打ち切って「途中まで分析」と表示する。
- **有効スタックに最も近い深度の解**（20/40/60/100/200bb、対数で最も近いもの）に照らして採点する。15〜250bb 以外は採点しない。各ハンドが使った解のIDは保存されるので、Studyへのリンク（`#d=40&n=…`）・練習セット（1つの深度の解にまとめる）も同じ深度になる。

### ポストフロップ
採点しない。代わりに、**ヘッズアップでフロップに進んだハンド**は、ラインから両者のレンジを復元して（各プレイヤーの最後の判断の `重み × 選んだアクションの頻度`）、フロップ・ポット・有効スタックと一緒に Solve 画面の下書きに入れて開く（「フロップをSolveで調べる」）。3人以上、プリフロップでオールインしたハンドは対象外。

### 弱点と練習セット
ポジション×局面タイプ別にEV損失を集計して上位を表示。「ミスしたハンドで練習セットを作る」は、不正確/ミス/大ミスの (ノード, ハンド) を損失の大きい順に最大30問、練習の固定リスト（`#set=<id>`）にして開始する。

## ログインとクラウド同期

```
supabase/schema.sql               テーブルとRLS（SQLエディタで1回実行。何度実行しても安全）
web/src/lib/sync/supabase.ts      GoTrue(メールのワンタイムコード) と PostgREST を fetch で呼ぶ（SDKなし）
web/src/lib/sync/engine.ts        同期アルゴリズム（バックエンドに依存しない）
web/src/components/sync/          SyncProvider（自動同期）, SyncPanel（設定画面）
```

### 設定（ビルド時）
`web/.env.local` に `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY` を置く（`web/.env.example` 参照）。無ければ同期UIは「未設定」と表示するだけで、アプリは従来どおり端末内で動く。**使うのは公開の anon キーだけ**で、`service_role` キーはクライアントに置かない。行レベルセキュリティで自分の行しか読み書きできない。

Supabase側: Authentication → Providers → Email を有効にし、「Magic Link」メールテンプレートに `{{ .Token }}`（6桁コード）を含める（既定はリンクのみ）。

### アルゴリズム（`syncOnce`）
1. **記録（attempts）** は追記のみ。未送信分（ローカルIDが前回送信済みより大きく、`remote` でないもの）を `on_conflict=user_id,client_id,ts,node_id,hand` + `ignore-duplicates` で送る。続けて `ts >= 前回の最大ts` を取得し、`(ts, node, hand)` が既にあれば捨て、無ければ追加して `remote: true` を付ける（= 送り返さない）。
2. **間隔反復（srs）** と **保存したレンジ** は項目ごとの Last-Writer-Wins（`updated` / `ts` が新しい方）。
3. **設定** は全体で新しい方（端末側の変更時刻は `localStorage` の `tessera.settings.updated`）。一度も変更していない端末は上書きしない。
4. 失敗したらカーソルを進めずに終了し、30秒から最大15分の指数バックオフでやり直す。自動同期のタイミング: 起動時、5分ごと(画面が見えている間)、フォアグラウンド復帰、オンライン復帰、設定画面の「今すぐ同期」。
5. 端末ごとの状態（`client_id`・各カーソル）は IndexedDB の `meta`（`sync.state.<userId>`）。

### 同期しないもの・制限（正直なリスト）
- 保存した Solve（大きい）と取り込んだハンド履歴は**端末内のみ**。
- **削除は同期されない**（墓標なし）。
- **実際のSupabaseプロジェクトに対しては未検証**。fetchの呼び出しは、PostgRESTとGoTrueの挙動（`on_conflict`、`Prefer`、`gte.` フィルタ、ページング）を模した偽サーバーでVitest・Playwrightにより検証している。本番でテーブル名・テンプレート等の設定違いがあると失敗する可能性がある（失敗は画面に出て、アプリは動き続ける）。
- 認証トークンは `localStorage` に保存する（サーバー側のセッション管理はしない）。
